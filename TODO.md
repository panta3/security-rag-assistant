## Notes
- Don't skip the eval harness — "I built a RAG app" is generic, "I measured X% retrieval precision and Y% citation accuracy" is not.
- Building the eval harness surfaced 3 real bugs, none in the core retrieval/generation logic:
  1. **My own eval set had wrong page numbers.** I confused the NIST document's own printed page footer (e.g. "26") with the PDF's physical page index our ingestion pipeline actually cites (there's a 5-page offset from the cover/abstract/TOC/preface). 10 of 24 expected_pages were off by exactly 5. This alone made retrieval_precision look like 29% when it was actually 50%.
  2. **`/ingest` wasn't idempotent** — chunks were keyed by `uuid.uuid4()`, so re-ingesting the same PDF (which I did repeatedly while testing) silently duplicated every chunk instead of overwriting it. Caught when a "clean" ingest showed 198 chunks in the vector store instead of 33. Fixed the same way as the Posture Scanner's DynamoDB bug: deterministic IDs (`source_doc#page#index`) plus Chroma's `upsert()` instead of `add()`.
  3. **The hallucination-rate detection logic itself was too crude.** Checking "citations non-empty" as the hallucination signal was wrong — the model can legitimately retrieve same-topic-but-insufficient context and still correctly decline in its own answer text (e.g. "the CSF does not specify a minimum number of firewalls"). Moved decline-detection into `rag.py` itself (`_is_decline`, checked against a phrase list) so both `answer_query()` and `evaluate()` share one definition of "declined."
- The distance threshold (`NO_MATCH_DISTANCE_THRESHOLD` in rag.py) was originally calibrated off two anecdotal examples and set too low (1.0), which the real eval set proved was blocking legitimately answerable questions (up to 1.385 distance). Recalibrated to 1.5 using the actual measured distribution. Also confirmed empirically: same-domain-but-fabricated questions (e.g. asking for a specific number the CSF never states) score in the *same* distance range as genuinely answerable questions (0.96–0.99) — no distance threshold can separate those two cases, which is exactly why the two-layer defense (threshold + prompt-level self-awareness) matters instead of relying on retrieval distance alone.
- Never run a standalone script against `chroma_data` while the FastAPI server is also running — two processes writing to the same on-disk Chroma SQLite file concurrently produced a corrupted count (198 chunks from what should have been a single clean 33-chunk ingest). Use the running server's own endpoints for everything once it's up.

## Deploying to Cloud Run — real bugs found, in the order they surfaced
1. **CPU inference was ~115x too slow to ship.** The first deploy attempt used the same full-precision `transformers`/`torch` setup as local dev (just switched `torch.cuda.is_available()` to pick `bfloat16` on CPU instead of `float16`). Measured: **0.26 tok/s** — a 40-token answer took 114.6s, so a full 512-token response would've taken 30+ minutes. Root cause: plain eager-mode PyTorch has no real optimization path for CPU inference, and bf16 specifically has no hardware acceleration on most cloud CPU platforms (needs AVX512-BF16, not guaranteed present). Considered switching to GPU-backed Cloud Run instead, but that trades real ongoing cost for a problem that's actually a software inefficiency, not a hardware limitation — fixed properly instead: rewrote `generation.py` to use `llama-cpp-python` against a Q4_K_M GGUF quantization of the same model (`Qwen/Qwen2.5-3B-Instruct-GGUF`). Measured after the fix: **9.64 tok/s**, a **~37x speedup**, model load time dropped from tens of seconds to ~2s. Also removed `torch`/`transformers`/`accelerate` as the LLM's runtime dependency entirely (they're still used for the small embedding model, which was never the bottleneck).
2. **ChromaDB's default telemetry can silently stall container startup.** After the GGUF fix, the first real deploy still failed Cloud Run's startup probe (`STARTUP TCP probe failed ... DEADLINE_EXCEEDED`). Chroma's `PersistentClient` phones home anonymized telemetry by default at init time; on a network that blocks or slows that outbound call (Cloud Run's egress), the call can stall client construction for a long time with no error, no log line, nothing — it just looks like the container is hanging. Fixed by passing `settings=ChromaSettings(anonymized_telemetry=False)` to `PersistentClient`.
3. **Cloud Run's default startup probe budget (~240s) was too tight regardless.** Loading a quantized LLM + embedding model + Chroma client on a cold container can legitimately take longer than the default. Fixed by passing an explicit `--startup-probe` on `gcloud run deploy` with a 600s budget (`periodSeconds=10,failureThreshold=60`) instead of accepting the default.
4. **Two separate IAM permission bugs blocked the Cloud Build step**, both on the *default* Compute Engine service account that `gcloud run deploy --source .` uses under the hood for newer GCP projects (which no longer grant these by default): missing `roles/storage.objectViewer` (`403` reading the uploaded source zip from GCS), then missing `roles/artifactregistry.writer` (image built fine, silently failed to push — `gcloud` just reported `Build failed; check build logs for details` with no other detail until `roles/logging.logWriter` was also granted to actually see the real error).
5. **Live production latency is real but bimodal.** First request after a fresh revision deploy: ~87s (cold instance, first-inference warm-up on top of the health check already having passed). Second/warm request: **19s**, close to the local benchmark. Worth knowing this pattern going in rather than reading a slow first request as a regression.
